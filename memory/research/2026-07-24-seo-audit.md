# SEO Audit — CertZen (certzen.app)

Date: 2026-07-24
Scope: Technical + on-page SEO, static review (no Search Console access available). CSR React SPA on Firebase Hosting.

## Executive Summary

The site has genuinely good SEO bones for a solo-dev SPA: multilingual `SEOHead` component with proper hreflang/x-default, per-page canonical + OG/Twitter tags, JSON-LD on exam-set landing pages, a sensible `robots.txt`, and a sitemap generator that pulls published exam sets from Firestore. But **the deployed `sitemap.xml` is stale and disconnected from the generator** — the site's highest-value indexable pages (individual exam-set landing pages, domain-filtered explore pages) are not in the sitemap Google actually crawls. There's also a `lang="en"` vs. Spanish-content mismatch in the static shell, and three different components independently emit `<head>` tags with inconsistent output (missing hreflang, wrong locale, no noindex logic in one path).

**Top priority issues:**
1. Production sitemap.xml has 9 URLs; the generator produces static + domain + per-exam-set URLs but is never run in the deploy pipeline.
2. `<html lang="en">` in index.html contradicts Spanish default content and `og:locale: es_ES`.
3. Three separate `<head>`-tag components (`SEOHead`, `PageSEO`, raw `<Helmet>` in `ExploreExamsPage`) duplicate logic and drift out of sync (only `SEOHead` emits hreflang).
4. Pure CSR with no prerendering — non-JS crawlers (LinkedIn, Slack, WhatsApp, Twitter/X) always see the homepage's static OG tags regardless of which page is shared.

---

## Findings

### 1. Sitemap is stale and not wired into deploy — HIGH
- **Evidence:** `public/sitemap.xml` (committed, deployed) has only 9 static routes. `scripts/generate-sitemap.mjs` fetches `examSets` from Firestore, plus 7 `DOMAIN_ROUTES` (`/explore?domain=X`), plus per-set `/exam-sets/:slug` URLs — none of which appear in the committed file. `npm run deploy` is `lint:critical && build && firebase deploy` — it never calls `npm run sitemap`. No `.github/workflows/` exists to run it in CI either.
- **Impact:** `/exam-sets/:slug` pages (which have JSON-LD + hreflang, built specifically to rank) rely entirely on organic discovery/internal links for indexing. This is likely the single biggest gap suppressing indexation of the content that matters most.
- **Fix:** Add `npm run sitemap` as a step before `firebase deploy` in the `deploy` script (or a pre-deploy CI step), so the file is regenerated from live Firestore data every deploy. Also reconcile `robots.txt`: the generator's version differs from the committed one (missing `/settings`, `/home`, `/payment-success`, `/folders/` disallows) — same root cause, same fix.

### 2. `<html lang="en">` contradicts Spanish content — MEDIUM
- **Evidence:** `index.html:2` sets `lang="en"`, but the static `<title>`, `<meta name="description">`, and `og:locale` (`es_ES`) are all Spanish. `SEOHead.jsx` correctly overrides `<html lang>` client-side per locale, but crawlers/screen readers that read the raw HTML (pre-hydration) see the mismatch.
- **Impact:** Minor ranking signal confusion + accessibility (screen readers may use wrong pronunciation rules) for the pre-render state, which is what non-JS bots see.
- **Fix:** Set `lang="es"` in `index.html` to match the default locale, since `es` is the fallback for any client that doesn't execute JS.

### 3. Three divergent `<head>` implementations — MEDIUM
- **Evidence:** `src/components/SEOHead.jsx` (multilingual, hreflang, correct per-locale `og:locale`), `src/components/seo/PageSEO.jsx` (hardcoded `es_ES`, no hreflang, has `noIndex` prop and JSON-LD support), and a third inline `<Helmet>` block directly in `ExploreExamsPage.jsx` (hardcoded `es_CO` — a third, different locale value — no hreflang, no `noindex` capability).
- **Impact:** Inconsistent hreflang coverage means only pages using `SEOHead` get correct international targeting; `PageSEO` and ad-hoc `Helmet` pages silently lack alternates. Three `og:locale` values (`es_ES`, `es_ES`, `es_CO`) across the codebase is a small but avoidable inconsistency.
- **Fix:** Consolidate on one component (`SEOHead` is the more complete one) or explicitly document when each is used. At minimum, standardize the `og:locale` default and add hreflang to `PageSEO` and the `ExploreExamsPage` inline block.

### 4. No prerendering — CSR-only social/crawler visibility — MEDIUM
- **Evidence:** `vite.config.js` has no prerender plugin; Firebase Hosting rewrites `**` → `/index.html` with no exceptions. `SEOHead`/`PageSEO` update tags client-side via `react-helmet-async` only after JS executes.
- **Impact:** Googlebot generally renders JS (mitigates this for Google specifically), but social-share crawlers (Facebook, LinkedIn, Slack, WhatsApp, X) and some SEO tools do **not** execute JS — every shared link (including `/exam-sets/:slug` pages meant to be shared) will show the generic homepage OG image/title/description baked into `index.html`, not the page-specific ones.
- **Fix:** Given the stack, cheapest fix is a small prerender step for the small set of public marketing/landing routes (react-snap, or Firebase's dynamic rendering via a Cloud Function that serves prerendered HTML to known bot user-agents) — full SSR migration is likely overkill for this codebase's size. Flag as a `research/` candidate before implementing per project convention.

### 5. `/explore?domain=X` as query-param filter pages — LOW
- **Evidence:** Domain-filtered explore pages use `?domain=` query strings, both as canonical (`ExploreExamsPage.jsx:199`) and in the sitemap generator's `DOMAIN_ROUTES`.
- **Impact:** Google can index parameterized URLs fine when self-canonicalized (which this does correctly), so this isn't broken — but path-based URLs (`/explore/appian`) are generally stronger for anchor-text relevance and cleaner sharing. Not urgent since the canonical is self-consistent.
- **Fix:** Optional — consider path segments if/when investing in category-page SEO; not a defect as-is.

### 6. Sitemap `lastmod` freshness — LOW
- **Evidence:** All static-route entries in the committed sitemap carry the same `lastmod` (2026-04-18), which is just the day someone last ran the generator manually.
- **Impact:** Minor — once sitemap generation is automated (finding #1), this resolves itself for dynamic entries; static route dates are cosmetic.

## What's already solid (no action needed)
- `robots.txt` correctly blocks private/auth-gated routes (`/exam`, `/results`, `/dashboard`, `/profile`, `/admin`) while allowing `/`, `/explore`, `/exam-sets/*`.
- Canonical tags present and self-referencing on all audited pages.
- JSON-LD structured data present on `ExamSetLandingPage.jsx`.
- OG/Twitter Card tags complete (title, description, image w/ dimensions + alt) on every page checked.
- `noindex` correctly applied to "set not found" state and admin/private pages.
- PWA manifest, favicons, apple-touch-icon all present.
- Fonts loaded non-blocking with preconnect; no obvious render-blocking CSS/JS SEO concern from static review.

---

## Prioritized Action Plan
1. **Critical:** Wire `npm run sitemap` into the deploy pipeline so exam-set/domain pages are actually discoverable.
2. **High:** Fix `<html lang="en">` → `es` in `index.html`.
3. **High:** Consolidate `SEOHead`/`PageSEO`/inline `Helmet` into one path so hreflang and `noindex` are applied consistently everywhere.
4. **Medium:** Evaluate prerendering for public landing routes shared on social platforms.
5. **Low:** Consider path-based domain URLs if category-page SEO becomes a priority.

- Actual index coverage / `site:certzen.app` status — needs Search Console access.
- Rendered JSON-LD validation — needs Rich Results Test (this review read source, not rendered DOM).
